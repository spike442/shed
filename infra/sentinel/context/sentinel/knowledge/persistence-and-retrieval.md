# Sentinel domain persistence and retrieval

Repository: `shed`. Scope: database ownership, domain history, and grounded agent input.

## Responsibilities

Sentinel stores current incidents, reviews, feedback, action results, and their UI-visible history in PostgreSQL.
PostgreSQL is the only store of incident and review records and their history; Sentinel keeps no separate archive
of them.
Agent workers have no platform status table. They receive commands and return decisions
through Kafka; Sentinel owns application database access.

PostgreSQL `incidents` and `pr_reviews` hold the current state in dedicated columns.
Structured values such as alerts, diagnoses, timelines, checks, and action histories each
have their own JSONB column. Domain repositories
create missing records with an atomic `INSERT ... ON CONFLICT DO NOTHING`, then lock the
row with `SELECT FOR UPDATE`. Inside that transaction the repository copies the row into a
frozen snapshot, asks the pure state machine (`shed/sentinel/workflow/src/sentinel/workflow/sre/incidents/machine.py`,
`pr_review/machine.py`) to decide the event at the database clock, and writes back only the
returned state: `Accepted`, `Unchanged`, `Rejected`, `Missing`, or `Removed`. The machines
never mutate inputs or perform I/O, and each `transition` rejects a status change that the workflow
graph in `shed/sentinel/core/src/sentinel/core/state/workflows.py` does not list; an outcome that keeps its status is
not a change. Changed JSONB values are written as new objects so SQLAlchemy detects them. A review's identity is
a stable UUID of its pull request (owner, repository, number), so every revision, replay, and fix of one PR is an
attempt of one row; incident identities remain alert fingerprints. Workflow IDs guard stale Kafka results.
Both domains keep their history in two append-only, never-trimmed JSONB columns built by
`shed/sentinel/core/src/sentinel/core/state/history.py`: `timeline` (status changes) and `attempts` (one entry per agent
run with its trigger, prompt, revision, status, result, audit actions, and tool budget). The other columns are the
latest view; an agent receives only the last five finished attempts, without audit trails
(`shed/sentinel/core/src/sentinel/core/contracts/history.py`).
UI deletion removes the incident or review row from PostgreSQL. A later alert or discovery
of the same PR can create a new row. The knowledge index retires documents whose
source row is absent on its next successful indexing run.

## Initialization and recovery

SQL lives under `infra/sentinel/sql/<version>/<engine>/<domain>/`. Installs always start from scratch from the highest version folder; there are no migrations, and a release in development edits its own folder in place. Initialize a fresh installation by hand
with `task sql MODULE=sentinel` (the Ansible playbook `infra/ansible/sql.yaml`) after Flux created the PostgreSQL database and
roles and the ClickHouse server, and after `task sql MODULE=knowledge` created the knowledge database, before deploying Sentinel;
`task s3 MODULE=sentinel` uploads its prompts and knowledge. Sentinel's inventory hosts are `sentinel-postgresql`,
`sentinel-clickhouse`, and `sentinel-s3`, with the engine settings in `infra/ansible/inventory/group_vars/<engine>/`, their own
in `host_vars/<host>/main.yaml`, and 1Password lookups in `secrets.yaml`. The SQL module is one `sql` role: it selects
the highest version folder under `infra/<module>/sql/`, finds the files of the host's engine folder there in path order, and hands them to
`roles/sql/tasks/<engine>.yaml`, which runs them in one session of the engine's own client. `psql`
connects as `sentinel`; `clickhouse client` connects to the native port as `admin`. Sentinel's ClickHouse SQL
(`clickhouse/30-knowledge/`) creates only its own knowledge tables, `knowledge.sentinel_documents` and
`knowledge.sentinel_chunks`, in the `knowledge` database the knowledge module creates. Both stop at the first error. A
release adds SQL by adding its version folder; a missing version folder or an engine folder that no
host in group `sql` deploys stops the module. The S3 module creates the Sentinel bucket with RustFS
credentials from 1Password, then uploads prompts and knowledge. The application does
not execute schema SQL. A fresh installation starts with empty domain tables.

Homelab provisions the ClickHouse server; the knowledge module creates the `knowledge` database and user. Installs are always
fresh; model files and knowledge vectors are regenerated by indexing.

## Knowledge indexing

Sentinel's knowledge is served by the Shed knowledge service (`shed/knowledge/`, the `knowledge` Deployment from
`infra/knowledge/chart/`), which Sentinel calls as the domain `sentinel` (`POST /v1/domains/sentinel/search`). Sentinel owns its
knowledge data: the documents in its `sentinel` bucket and its two tables in the knowledge service's `knowledge` ClickHouse
database (`knowledge.sentinel_documents` and `knowledge.sentinel_chunks`, created by
`infra/sentinel/sql/<version>/clickhouse/30-knowledge/`). The knowledge chart's `config/knowledge.yaml` names those tables, the
bucket, and the collections, and the knowledge Deployment reads the bucket with Sentinel's S3 credential from its own
`knowledge-secrets`.

Repository knowledge in `infra/sentinel/context/<repository>/knowledge/` is published to
`s3://sentinel/context/<repository>/knowledge/`. Metadata lists eligible domains so SRE and PR Review
share content and embeddings. Agent instructions live alongside it in
`infra/sentinel/context/<repository>/prompts/<agent>/` and are excluded from knowledge indexing.

Each of Sentinel's `collections` names a context collection (`name`, indexed from `context/<name>/knowledge/`)
and the agents that may retrieve its files (`tags`, the agent domains `sre` and `pr-review`), and a search returns only
the knowledge of the collection it is for: PR Review loads `homelab` knowledge for a `homelab` pull request and
`dotfiles` knowledge for a `dotfiles` one, while SRE, which investigates only `homelab`, retrieves only
`homelab` knowledge. Only these S3 knowledge files are indexed. Incident and review records are not: their audit trails are
raw tool output that would crowd out the curated documents. The knowledge service has no PostgreSQL access.
Learning means retrieving evidence, not training the LLM.

The knowledge service loads the pinned ONNX model from the `knowledge` image once and
shares it between search and indexing. It counts tokens and generates embeddings in process,
so splitting and retrieval do not make per-chunk HTTP requests.
Documents and queries have distinct task prefixes. Model revision, dimensions, and chunking form
an indexing signature; changing them rebuilds embeddings.

`sentinel_documents` holds source content, tags, collection, revisions, and published generations.
`sentinel_chunks` holds text and vectors with text and HNSW indexes. Chunks are inserted before
their generation is published, keeping incomplete documents invisible. Objects missing from S3 are
retired after successful ingestion of all of Sentinel's collections.

Indexing runs in a background thread of the knowledge service, on startup and every
`rag.index_interval_seconds`; a failed pass of a domain is logged and retried within 60 seconds
without stopping the other domains. The Deployment has one replica and the `Recreate` strategy, so passes never overlap. Keep
configured S3 prefixes limited to knowledge documents. Sentinel's search answers 503 until its first pass succeeded; the service is
ready once every domain had a first pass and ClickHouse answers. A later failed pass keeps serving the existing index.

## Retrieval

Sentinel preloads RAG context from the knowledge service before each SRE investigation or PR review. The API filters by
collection and tag, ranks chunks by embedding similarity, and applies
result/token budgets. Excerpts carry source and chunk references into worker input. The agents can
also call `search_knowledge` for focused follow-up questions through the knowledge
service. The tool keeps the same collection and tag scope and result budget as the preload. Historical
proposals are evidence to evaluate, not instructions or current cluster state.

The model generates vectors in the knowledge service; ClickHouse stores and
searches them. Only the knowledge service contacts ClickHouse. Mandatory prompts and live tool
verification remain necessary.
