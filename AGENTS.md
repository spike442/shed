# Shed agent instructions

These rules apply to every coding agent working in this repository (Claude Code reads them through `CLAUDE.md`, Codex and others read `AGENTS.md` directly).

Shed is one project with four modules and two shared libraries: `shed` (the door to the platform: one image and Deployment whose API serves the SRE domain and whose bundled UI shows every domain backend), `knowledge` (the knowledge service every domain searches its own knowledge through), `sentinel` (the SRE domain: incident and pull request review workflows, their agents, and the executor), and `stonks` (the Stonks data platform), plus the libraries `core` (`shed-core`) and `agents` (`shed-agents`, the agents framework), which have no image or chart. Each module is a folder of uv workspace members under `shed/` (the Python parent, holding the workspace and its lockfile) and a folder of infrastructure under `infra/<module>/` (its Helm chart, and its context, SQL, reference documents, or Airflow DAGs); `infra/ansible/` is shared. The modules share one workspace and one lockfile in the GitHub repository `spike442/shed`; each module has its own version, release tag (`<module>-<version>`), images, and chart, released by Publish only when it changed.

## Start here

- Work from the repository root. Check `git status --short` and preserve existing edits.
- Use the source map below; check the relevant `infra/sentinel/context/sentinel/knowledge/` document against current code.
- Make deployment changes in Git. Homelab is a separate GitOps repository; do not edit the live cluster. Installs are always fresh: do not add backup, restore, upgrade, or migration paths.
- Do not commit, push, or publish unless asked.

Each deployable module has its own project and image. State changes belong to the workflow;
the API reads records and publishes operator requests over Kafka. Decisions live in pure modules;
I/O lives at the edges.

- The SRE domain's two workflows live under `shed/sentinel/workflow/src/sentinel/workflow/sre/`: `incidents/` (run by the SRE agent) and `reviews/` (run by the PR Review agent). One switch, the chart's `agents.sre.enabled`, enables the SRE domain and both agents (it renders `agents: [pr-review, sre]`). The two share one layout. `snapshot.py` (frozen record
  snapshot), `events.py`, and `machine.py` form the pure state machine: every change is a
  function `(snapshot, event, now) -> Outcome` listed in `TRANSITIONS`. Status sets are
  pure rules in `shed/sentinel/core/src/sentinel/core/state/incident_rules.py` and `review_rules.py`, shared with the API. `repository.py` applies events through
  `postgres.apply_event` (lock, snapshot, transition, write) and persists rows defined in core.
  `shed/shed/api/src/shed/api/requests.py` publishes operator requests. Each domain's `workflow.py` is a
  `DomainWorkflow` (`shed/sentinel/workflow/src/sentinel/workflow/routing.py`): its tables map each topic, request kind,
  and executor action to the component that owns it, and `__main__.py` builds the consumers from those tables.
  `DomainWorkflow` itself fails the record a failed message names, deletes records, and expires stalled runs for
  every domain; each domain passes only its records, active statuses, timeout rule, and timeout. Every Kafka
  message about a record is a `RecordMessage` (`record_id` and `workflow_id`), and a failed agent run returns a
  `RunFailure`; every repository fails a record with `fail(record_id, workflow_id, failure)` and removes one with
  `delete`, and `DomainMessages.fail` fails and announces in one call.
  `shed/sentinel/workflow/src/sentinel/workflow/messages.py` (`DomainMessages`) is every domain's Kafka side (agent
  commands, executor commands, scheduled requests) and its Discord notifications;
  `shed/sentinel/workflow/src/sentinel/workflow/__main__.py` starts both enabled workflows. The workflow owns PostgreSQL transitions and
  decide every external side effect, but perform none: they publish typed
  `ExecutorCommand`s and apply the matching `ExecutorReturn`.
- Incident components: `investigation.py` (cluster alerts, agent runs, timeouts, and skipping alerts that
  `alertmanager.py` no longer reports firing), `submission.py`
  (claim a fix and apply the executor's pull request), and `manual_actions.py` (claim, run, record,
  expire). Incidents also add the pure `fix_policy.py`; the API normalizes Alertmanager webhook alerts before
  publishing them.
- Review components: `discovery.py` (open pull requests to review), `review.py` (agent runs and
  timeouts), `merge.py` (approved merges), `replay.py` (reconcile and review again), and `fix.py` (an operator's Fix it
  of a blocked review: the reviewer's fix, the pure `fix_policy.py`, and the executor's push), and `incident_link.py`
  (`IncidentLink`: a review of an incident's fix pull request, matched by the PR URL the incident recorded, keeps the
  `incident_id`, and the incident keeps the `review_id` and records the review starting and its final status as
  `fix_review_<status>` timeline events, without changing its own status). A review is one record
  per pull request; reviews of every other pull request have no incident. The API lists the link on both records as
  `links`, and the UI shows it as a button to the other record. Both domains keep every agent run as an attempt and every status change in a timeline, never
  trimmed, through the pure `shed/sentinel/core/src/sentinel/core/state/history.py`. Discovery, replay, and fix
  read GitHub directly through `shed/sentinel/core/src/sentinel/core/github.py` (`GitHubReader` with `READ_ONLY` tokens).
- `shed/sentinel/executor/` holds `actions.py` (one idempotent handler per `ExecutorAction`; every action changes something), `github.py` (the write gateway on the core `GitHubReader`),
  `git_workspace.py`, `commands.py` (bounded manual-action runs), `settings.py`, and `worker.py`.
- `shed/sentinel/core/src/sentinel/core/state/outcomes.py` defines pure transition outcomes and the `require_*` helpers that
  map them to `NotFound` and `Conflict` errors at the repository boundary.
- Agents hold only what a model needs to do one job, never a workflow, storage, scheduling, or a decision about what is kept.
  - `shed/agents/src/shed/agents/` is the framework shared by every agent: `runner.py` (the one agent contract: `AgentConfig` with the model and the per-tool call limit, `RunContext` with the audit log and deadline every tool context extends, `AgentTask` naming an agent's action, tools, tool context, and structured answer, `AgentRun` carrying one run's prompt scope, message, context, and trace metadata, and `AgentRunner`, which builds the system prompt as `system.md`, then `actions/<action>.md`, then `actions/<tool>.md` for every tool, compiles one agent per task and scope, runs it, records its tool budget, and checks its answer), `langchain.py` (`chat_model`, `structured_agent` with its per-tool limits and run-deadline middleware, `tool_budget`), `audit.py` (the LangChain audit middleware), `prompts.py` (`PromptStore`, reading `context/<scope>/prompts/<agent>/<name>` once per process through an S3 client the caller owns; the scope is a Sentinel repository or `stonks`). In `shed/sentinel/agents/src/sentinel/agents/`, `sre/knowledge.py` holds `KnowledgeContext`, reference material, and the `search_knowledge` tool both SRE agents share.
  - Agent packages live with their domain: `sre/incident/` (the SRE agent) and `sre/review/` (the PR Review agent) in `shed/sentinel/agents/`, and the dividend agent in Stonks as `shed/stonks/dividends/src/stonks/dividends/agent/`; each imports only `shed.agents`, never another agent. Each agent package declares only its domain: `agent.py` holds its `AgentTask`s (`sre/incident`: `INVESTIGATE`; `sre/review`: `REVIEW` and `FIX`; `dividends`: `RESEARCH`) and a typed facade (`DiagnosisAgent`, `ReviewAgent`, `DividendAgent`) that builds the run's message and tool context and calls the `AgentRunner` it is given, and `tools.py` holds the tool context and tools. An agent's prompt folder is its task's `agent` name (`sre`, `pr-review`, `dividends`). Agents take plain values, never a worker's settings: `settings.py` holds only the config models their tools need (SRE `ShellConfig` and `PrometheusConfig`, Dividends `ExcerptConfig`). SRE adds `commands.py` (`CommandRunner`, bounded read-only shell pipelines) and `prometheus.py` (`Prometheus`); PR Review adds `checkout.py` (the checkout paths `read_file` and the fix check share); Dividends adds `contracts.py` (`Security`, `SearchResult`, `DividendAnswer` with one `SourceQuote` per fact) and `excerpt.py`, and takes its search and page reader from the domain as `ResearchSources`.
  - `shed/agents/ruff.toml` bans imports of every other module (`sentinel`, `stonks`, `shed.api`, `knowledge`), `shed/knowledge/ruff.toml` bans `sentinel`, `stonks`, `shed.api`, and `shed.agents`, and `shed/sentinel/agents/ruff.toml` every deployable (`stonks`, `sentinel.sre`, `sentinel.workflow`, `sentinel.executor`, `shed.api`, `knowledge.api`).
- `shed/sentinel/sre/src/sentinel/sre/worker.py` is the one SRE process: it builds both runtimes and runs both agents in one container through `run_agents` (`shed/sentinel/core/src/sentinel/core/kafka/agent_worker.py`: one thread per `Agent`, one signal handler, and every agent stops when one ends). `incidents/` and `reviews/` share one flat layout:
  `runtime.py` (a context manager that builds the S3 client, prompts, knowledge client, `AgentRunner`, and agent, and owns their lifetime),
  `run.py` (the deterministic steps of one investigation or review: `IncidentInvestigation`, `ReviewRun`), and `settings.py` (the worker's YAML files, environment prefix, and limits on the core `AgentSettings`, with an `agent` property giving the `AgentConfig`; the Stonks dividends settings expose the same property). PR Review adds the pure `policy.py` and `workspace.py`.
  `shed/core/src/shed/core/deadline.py` holds the run deadline every agent run and executor action stops at, and `shed/core/src/shed/core/audit.py` the `AuditLog` and `ToolBudget` every agent run records. The agents framework depends only on `shed-core` and LangChain, so the dividend agent, and Stonks with it, never depends on Sentinel.
`shed/shed/api/src/shed/api/lifespan.py` builds the API's settings, database, and metrics; workers construct only the clients they use. The process entry
points are `shed.api.server`, `knowledge.api.main`, `sentinel.workflow`, `sentinel.executor.worker`,
and `sentinel.sre.worker`.

### Working in this repository

Run `task setup` from the repository root. The Python workspace is `shed/` (root project `shed-workspace`); run `uv` package
commands there. The React app is `shed/shed/ui/`. Run the nine startup tests with
`cd shed && .venv/bin/python -m pytest -q`, then check Python with
`shed/.venv/bin/ruff check shed infra/stonks/airflow` and `shed/.venv/bin/ruff format --check shed infra/stonks/airflow`.
CI (`.github/workflows/ci.yml`, on pull requests, `main`, and weekly) and Publish both run `.github/workflows/shed.yml`: Python
checks, the UI build, the DAG import, chart checks, a non-blocking dependency audit (`pip-audit`, `npm audit`), and one image job per
image. Nothing lists the images: `shed/<module>/Dockerfile` is the image `<module>` (`shed`, which builds the UI into the API image) and every `shed/<module>/<member>/Dockerfile` is the image `<module>-<member>`. A module's paths are its
`shed/<module>/` and `infra/<module>/` folders, the workspace files, `shed/core`, and the other libraries its images copy (`shed`:
`knowledge/client` and `sentinel/core`; `sentinel`: `agents` and `knowledge/client`; `stonks`: `agents`). On a pull request `dorny/paths-filter` builds only the images of the
modules whose paths changed (or all, when `shed.yml` changed); every other CI run builds all of them, and outside pull requests each
built image is scanned with Trivy (HIGH and CRITICAL with a fix) into GitHub code scanning. The core library is installed only as a
dependency. Each module has its own version and release, recorded in the repository like a Maven multi-module build: every project of a module, its libraries included (`sentinel/core`
and `sentinel/agents` carry Sentinel's version), `uv.lock`, and its chart's `version` and `appVersion` carry the module's last
released version; the library modules `core` (`shed-core`, whose version the workspace root carries too) and `agents` (`shed-agents`) are released the same way with no image or chart, their paths being their folder, `shed/core`, and `shed/pyproject.toml`. A library release releases every module that builds from it, because their paths include it: `core` releases every module, `agents` Sentinel and Stonks. Publish (`.github/workflows/publish.yml`) is started by hand on `main`. One `paulhatch/semantic-version` step
per module (`core`, `agents`, `knowledge`, `shed`, `sentinel`, `stonks`) finds that module's last `<module>-<major>.<minor>.<patch>` tag, reports whether its paths changed since (its folders, `shed/core`, the libraries it builds from, and another module's library it copies (`sentinel/core` for shed, `knowledge/client` for shed and Sentinel) without its
`pyproject.toml`, which on that module's release commit only carries its version, and `shed/pyproject.toml`; not `uv.lock`, which every
release rewrites), and computes the
next version from the Conventional Commits since that tag (`feat:` minor, `!:` or `BREAKING CHANGE:` major, anything else patch; a
module never released counts from `0.0.0`). Images are stamped only on Publish (each Dockerfile's `VERSION` build argument); CI builds keep the repository's versions and are tagged `ci`. Only the changed modules are released: their images are built with the version stamped
into every package by each Dockerfile's `VERSION` build argument (replacing whatever version the files hold) and pushed as `ghcr.io/spike442/shed/<image>:<version>`, their charts
are published as `oci://ghcr.io/spike442/charts/shed/<module>`, and workloads pull with `IfNotPresent`. Once everything is published,
Publish writes each released module's version into its projects, `uv.lock`, and chart, commits that to `main` as
`chore(release): …`, and tags that commit `<module>-<version>` (so the version commit belongs to the release and a rerun releases
nothing), then sends a `shed-release`
repository dispatch to Homelab, whose Renovate commits the released chart versions, and for Stonks the Airflow `STONKS_VERSION` and the
`stonks` release tag Airflow git-syncs the DAGs from (`dags.gitSync.ref`), to Homelab `main` in one group, so the DAGs always match the
Stonks images they run. Workstation CLI tools come from dotfiles, while
CI installs its pinned Helm version with `azure/setup-helm`.
Read `infra/sentinel/context/sentinel/knowledge/` for behavior and deployment boundaries before changing
a component. Deployment changes belong in Git; Homelab owns external databases, Kafka,
secrets, and site values.

## Stonks

Stonks is the European momentum swing-trading data platform: free end-of-day data for the PEA-eligible STOXX Europe 600
constituents the broker trades, a dividend agent whose findings are stored only after validation, and Spark layers.
Use only free data sources.

- `shed/stonks/ingest/src/stonks/ingest/` keeps `main.py` (entry point and `STEPS`, the step registry) and `runtime.py` (a context manager that builds every client and owns their lifetime) at its root. Everything else lives in one package per boundary:
  - `domain/` is pure and imports only the standard library: `models.py` (frozen `Constituent`, `Rejection`, `Selection`, `Candidates`, `Instrument`, `Universe`, `Country`, `Listings`), `records.py` (every document format in both directions: `countries.json`, the candidates and universe snapshots, and the watermarks), `pea.py` (the PEA countries, and ISIN country in a PEA country, minus the `pea.exclude` tax-exempt property companies in `ingest.yaml`, rejecting repeated ISINs), `listings.py` (the tradable `Listings` of the PEA countries, the tradable-listing filter, choosing a Yahoo listing on a tradable venue, and applying overrides), `universe.py` (the size guard, building the universe from the candidates, rejecting unresolved symbols and two ISINs on one symbol), and `bars.py` (`BarWatermark`, the fetch plan per instrument, and the split refresh rule). Domain functions take plain values, never settings or vendor payloads.
  - `sources/` holds inbound adapters that turn vendor formats into domain values: `xtrackers.py` (the STOXX Europe 600 constituents download and parser), and `yahoo.py` (`YahooSearch`, `YahooChart` for daily bars with dividends and splits, and their response readers, which date bars in the exchange's own timezone).
  - `storage/` holds `store.py` (`IngestStore`, typed reads and writes on the core `ObjectStore`: raw sources, `SymbolLookup` and `ChartFetch` records, the dated universe snapshot, `reference/countries.json`, and the `reference/` documents for the ISIN to Yahoo symbol cache and the per-ISIN bar watermarks). Steps never build storage keys or JSON.
  - `steps/` holds one class per ingest step (`UniverseStep`, `SymbolsStep`, `BarsStep`): the only code that combines sources, storage, and domain.
  - `config/settings.py` holds the YAML and environment settings.
- Dependencies point one way: `main` → `steps` → `sources` / `storage` → `domain`, and every package may use `stonks.core`. `domain` imports nothing from the other packages, and `sources` and `storage` never import each other or `steps`.
- `s3://stonks/reference/countries.json` (source `infra/stonks/reference/countries.json`, uploaded by `task s3 MODULE=stonks`) holds every per-exchange setting, keyed by ISIN country code, for the countries whose exchange the PEA broker trades (BoursoBank: BE, DE, ES, FR, IT, NL, PT): `name`, `pea` (companies registered there are PEA-eligible), `exchange` (its name in the constituents file), Yahoo `suffix`, `mic` (`exchange_calendars` code), and `filing_domains` (that market's official filing and exchange-notice sites). The universe and symbols steps and the agent's `validate` step read it at their start and fail when it is missing. The universe step keeps a constituent only when its ISIN country is listed with `pea` and its listing is one of these exchanges, decided before any Yahoo call: its `symbol_overrides` symbol, else its named main exchange, else, when the file names no exchange, its ISIN country's exchange. An override moves a stock to a tradable listing (`IAG.MC`). Companies registered in a country without an entry are left out (today ArcelorMittal and Tenaris, both Luxembourg); adding a country is one entry. Yahoo search accepts only these suffixes; the agent checks ex-dates on the listing's calendar and accepts the listing country's `filing_domains` besides `validation.newswire_domains`.
- The universe is keyed by ISIN. The Yahoo symbol is only the fetch key: the `symbols` step, separate from the universe selection, resolves it once per ISIN through Yahoo search, accepted only with a tradable suffix, and cached in `reference/yahoo-symbols.json`; `universe.symbol_overrides` in `ingest.yaml` sets the listing for ISINs search gets wrong or that trade on a second venue. `universe.ignored` maps each constituent line that is not a separate security to the reason it is dropped (French loyalty-bonus share lines, a secondary Unipol line); the universe step removes them first.
- Airflow orchestrates the daily run from the DAGs in `infra/stonks/airflow/dags/`; the modules themselves never schedule, sequence, or gate steps. `stonks_daily` runs `universe` → `symbols` → `bars` → `spark` at 18:45 Europe/Paris on weekdays, and `stonks_dividends` runs `research` → `validate` at 19:30. The DAGs share nothing but S3: when the universe is not there yet, `research` fails and its retry picks it up. `stonks_pods.py` builds every task: a `KubernetesPodOperator` in the `agents` namespace on the Pod template `templates/stonks-pod.yaml` (the `stonks` service account without a token, the namespace's restricted pod security, the `stonks-config` ConfigMap at `/etc/stonks`, resources, and an `IfNotPresent` pull of the immutable release image), adding only the module image with `<step> --trade-date <date>` and, through the provider's `Secret`, the `stonks-secrets` keys the module needs. The end of a failed step's output becomes the pod's termination message (`FallbackToLogsOnError`), which Airflow shows as the task's error, and its container states and events go to the task log; every pod is deleted when it finishes. The dividends steps, which read pages of up to `pages.max_bytes`, override the template's resources. The SparkApplication template sets resources only through the operator's fields (`cores`, `coreRequest`, `memory`, `memoryLimit`) and runs with a read-only root filesystem, writing only to its `/tmp` and `/opt/spark/work-dir` empty volumes. `spark` submits `templates/stonks-spark.yaml` through the Spark operator as `stonks-spark`. The trade date is the run's date in Europe/Paris, or the `trade_date` param of a manual run. Images are `<stonks_registry>/stonks-<module>:<stonks_version>`, from the Airflow Variables Homelab sets (`AIRFLOW_VAR_STONKS_VERSION`; registry and namespace default to `ghcr.io/spike442/shed` and `agents`). Each ingest invocation is `python -m stonks.ingest.main <step> --trade-date YYYY-MM-DD` (the image's entrypoint) and runs one step for one trade date. A step reads only what earlier steps wrote to S3 (the universe step writes `universe/trade_date=<trade_date>/candidates.json`, the PEA-eligible and tradable constituents, for the symbols step, which writes `universe/trade_date=<trade_date>/universe.json` for the bars step, the agent, and Spark), never Airflow state. A failing step exits non-zero and Airflow owns retries and alerting; `HttpSource` retries only transient HTTP errors inside one request. The DAG must run one trade date at a time (`max_active_runs=1`): the bar watermarks are shared state.
- Steps are safe to rerun. The candidates, the universe snapshot, and the references are overwritten; the universe step fails when fewer than `universe.min_instruments` constituents are eligible, and the symbols step when fewer instruments resolve. Raw is append-only: every run writes a new file stamped with its start time (`constituents-<downloaded_at>.csv`, `lookups-<started_at>.jsonl`, `chart-<fetched_at>.jsonl`, `research-<started_at>.jsonl`) and never replaces an earlier one, so a rerun of a trade date keeps the first run's evidence; readers keep the newest valid record.
- Yahoo prices and volumes are split-adjusted, not dividend-adjusted (`adjclose` is both), and a split rewrites the whole history. A watermark (`symbol`, `first_date`, `last_date`, known `splits`) plans each fetch: no watermark or a new symbol fetches `bars.history_years`; otherwise the fetch starts `bars.overlap_days` before `last_date` to pick up Yahoo corrections, and a trade date the watermark already covers is skipped, so reruns of past dates make no calls. A response carrying a split the watermark has not seen is refetched in full from `first_date` in the same run; if that refetch fails, the incremental fetch is recorded as failed so no reader mixes scales. Only bars with a close count: a trade-date bar without prices (Yahoo's late-night rollover) fails the instrument and leaves its watermark. Watermarks never move backwards. The step fails when more than `bars.max_failure_ratio` of the attempted instruments failed.
- Quote two-letter country codes such as `"NO"` in YAML; unquoted, YAML reads them as booleans.
- `shed/stonks/dividends/src/stonks/dividends/` mirrors the ingest layout (`main.py` with `STEPS` and each step's settings and runtime, `runtime.py`) and runs its own dividend agent (`agent/`, on the `shed.agents` framework); every rule that decides what is stored lives here:
  - `domain/` is pure and imports only the standard library: `models.py` (`Instrument`, `Venue`, `Evidence`, `Finding`, `Page`, `DividendDates`), `records.py` (the universe snapshot, `countries.json` venues, and `dividend-dates.json` formats), `selection.py` (which ISINs are due: never researched first, then the oldest check; a confirmed upcoming ex-date is not researched again), `evidence.py` (text normalization, verbatim quote matching, date and amount mentions in a quote, and allowed hosts), and `validation.py` (the rules that turn a `Finding` into `confirmed`, `declared`, or `unknown`).
  - `sources/` holds inbound adapters: `searxng.py` (the Homelab SearXNG JSON API) and `pages.py` (`PageReader`: HTML and PDF to text), which `runtime.py` hands to the agent as its `ResearchSources` and the validator reuses, and `venues.py` (`ListingVenues`: a listing suffix's exchange sessions from `exchange_calendars` through its `mic`, and its `filing_domains`).
  - `agent/` is the dividend agent, the only LangChain code in Stonks: `agent.py` (`RESEARCH` and the `DividendAgent` facade), `tools.py` (the tool context and tools, taking search and the page reader from `runtime.py` as `ResearchSources`), `contracts.py` (`Security`, `SearchResult`, `DividendAnswer` with one `SourceQuote` per fact), `excerpt.py`, and `settings.py` (`ExcerptConfig`). It imports only `shed.agents` and `shed.core`, never the rest of the module.
  - `storage/` holds `store.py` (`DividendStore`, on the core `ObjectStore`: the universe snapshot, append-only research records, and `reference/dividend-dates.json`).
  - `steps/` holds `ResearchStep` (the research queue, one `Security` per due ISIN for `DividendAgent.research`, and the raw record of every answer and audit trail) and `ValidateStep` (the agent's `DividendAnswer` mapped to a domain `Finding`, then validated). Dependencies point `main` → `steps` → `sources` / `storage` → `domain`; `runtime.py` and `steps` also use `agent/`.
  - Prompts live in `infra/stonks/context/stonks/prompts/dividends/` (`system.md`, `actions/research.md`, and one `actions/<tool>.md` per tool); the agent reads them with the prompt scope `stonks` from `s3://stonks/context/stonks/prompts/dividends/`; rerun `task s3 MODULE=stonks` after changing them.
- The dividend workflow is two Airflow tasks after the universe step. `research` takes at most `research.max_instruments` due ISINs, runs the agent once per ISIN under `limits.run_timeout_seconds` and `limits.max_tool_calls` per tool, and appends every answer, quote, error, and audit trail to `raw/source=dividend_agent/trade_date=<trade_date>/research-<started_at>.jsonl`; it fails when more than `research.max_failure_ratio` of them failed. `validate` reads the newest research per ISIN for the trade date, fetches every cited page itself, and stores a fact only when its source is allowed (`validation.newswire_domains`, the listing country's `filing_domains`, a `validation.issuer_domains` entry, or a host that contains a word of the issuer's name outside `validation.name_stopwords`), the quote is on the page verbatim, and the quote states that date or amount. An ex-date is stated or derived from a verified record date on the exchange calendar; a stated date that conflicts with the derived one, a non-trading day, or a passed date is rejected. Only a verified amount and payment date make a `declared` entry (`ex_date_before` the payment date). Everything else is `unknown` with its reasons; an `unknown` result never replaces a still-upcoming `confirmed` or `declared` entry. Agent failures are skipped so the ISIN is researched again.
- `shed/stonks/spark/src/stonks/spark/` is flat: `main.py` (entry point and Spark session), `config.py` (YAML config), `s3.py` (S3A options from the S3 site values and credentials), `daily.py` (one daily run: paths and orchestration), `readers.py` (explicit schemas and every `spark.read`: raw Yahoo charts and the universe snapshot), `writers.py` (every write: the prices table), and `bars.py` (pure DataFrame transformations: `yahoo_bars` keeps successful fetches dated up to the trade date, dates each bar in its exchange timezone, drops unpriced bars, keeps only the instrument's current symbol from the trade date's universe, and takes the newest fetch per ISIN and day; `latest_prices` keeps each instrument's newest bar). The `curated/` zone belongs to Spark alone: each run writes `curated/prices/trade_date=<trade_date>/`, one Parquet file with each instrument's latest bar up to the trade date (`isin`, `symbol`, `bar_date`, `open`, `high`, `low`, `close`, `volume`, `currency`, `exchange`), replacing that trade date's folder, so a rerun is idempotent and a past trade date keeps its point-in-time prices. The image adds the S3A connector pinned to Spark's Hadoop: `hadoop-aws` 3.5.0 and the AWS SDK `bundle` 2.35.4. PySpark comes from the pinned `apache/spark` base image.

The Stonks entry points are `stonks.ingest.main`, `stonks.dividends.main`, `stonks.spark.main`, and `stonks.api.server`. Raw data is immutable; every Spark layer is
rebuilt from it and replaces only its trade date's partition, so a rerun of a trade date is idempotent. The only model calls in Stonks are the dividend agent's `research` step, and nothing it says is stored without the
`validate` step's checks.


The Stonks modules read their configuration from `STONKS_CONFIG_DIR` (default `/etc/stonks`), a flat directory: `common/logging.yaml`, `common/storage.yaml` (the `raw`, `universe`, `reference`, and `curated` prefixes every module shares), `common/llm.yaml` for the dividend agent (read only by `research`, whose `ResearchSettings` and `research_runtime` add the model and agent to the `validate` step's `Settings` and `dividend_runtime`), `ingest.yaml` or `dividends.yaml` from `infra/stonks/chart/config/`, and `s3.yaml`, a site value Homelab owns; Spark reads only `logging.yaml`, `s3.yaml`, and `storage.yaml`. Credentials (`S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, and the dividend agent's `LLM_API_KEY`, required only by `research`) come from the environment as `SecretStr` and are unwrapped only at client boundaries. Homelab owns the `stonks` bucket credentials, the `stonks-secrets` Secret, the chart release and its site values (`s3`, `search.url`, `llm`), and Airflow's git-sync of the DAGs from the release tag, `AIRFLOW_VAR_STONKS_VERSION`, and remote task logs (`s3://logs/airflow`, in the `logs` bucket `task s3 MODULE=stonks` creates, through the `s3_logs` connection, built from the `stonks` item's S3 credential, so the UI reads a task's log after its worker pod is gone); the dividend agent searches through the SearXNG instance Homelab runs in `agents` (`search.url`). Stonks Spark code keeps `requires-python >=3.10` and reads plain YAML.

## Code style

- Write no comments in any language (Python, TypeScript, YAML, SQL, Helm templates, Ansible). Name things so the code explains itself and put explanations in `infra/sentinel/context/sentinel/knowledge/` or the source map in this file. Write no one-line Python docstrings; multi-line docstrings stay. The exceptions are docstrings the runtime reads: a LangChain `@tool` function's docstring is its description for the model, and a Pydantic model's class docstring is its JSON schema description in structured answers (`ProposedChange`, `PrFix`). Keep only functional comments: shebangs, `# yaml-language-server:` schema hints, `# renovate:` markers, `# vX` pins after action SHAs, Dockerfile `syntax=`, lint directives (`# noqa`, `# type: ignore`), and `/// <reference>`.

## Architecture

- `shed/pyproject.toml` and `shed/uv.lock` define the uv workspace (root project `shed-workspace`). Its members are `core/`, `agents/`, `knowledge/{api,client}/`, `shed/api/`, `sentinel/{agents,core,executor,sre,workflow}/`, and `stonks/{api,core,dividends,ingest,spark}/`, relative to `shed/`; a member depends on another through `{ workspace = true }` without a version pin (the workspace keeps them in step), so any module may use the shared libraries, as `stonks-dividends` uses `shed-agents`. `core` (`shed-core`), `agents` (`shed-agents`), `knowledge/client`, `sentinel/core`, `sentinel/agents`, and `stonks/core` are libraries the images copy into their builds; every other member owns a Dockerfile and startup test. Spark belongs to Stonks only: its code lives in `shed/stonks/spark/src/stonks/spark/`, and PySpark comes from its pinned base image; Sentinel runs no Spark.
- `shed/sentinel/core/src/sentinel/core/` is one shared namespace. `domain.py`, `contracts/`, and `state/outcomes.py` contain pure shared types; runtime adapters such as `config/`, `kafka/`, and `postgres.py` may depend on them, but pure modules do not import runtime adapters.
- Shed is one UI over one backend per domain, each under `/api/<domain>`. Every domain backend serves the same contract: `GET manifest` (`id`, `label`, `icon`, `kind` `workflow` or `data`, `version`, `enabled`, `running`, `active`, and for a `workflow` domain its `workflows`, each with the agent that runs it, whether that agent is running, and its active count), and, for each workflow of a `workflow` domain under `/api/<domain>/<workflow>`, `GET workflow` (states with their tone, transitions, and every status tone), `GET records` and `GET records/{id}` (each record with its `title`, the `actions` its status allows, and `links` to related records in other workflows), and `POST records/{id}/actions/{name}` (rejected with 409 unless listed), plus the domain's own `POST events/<event>` routes; a `data` domain serves `GET datasets`, `GET datasets/{name}?trade_date=`, and `GET trade-dates`, each dataset as `columns` and JSON `rows`. `shed/shed/api/src/shed/api/domains/` holds the contract (`contract.py`), the generic workflow router (`workflow.py`, `RecordWorkflow`), the generic domain router (`domain.py`, `ConsoleDomain`: one switch, its workflows, and its events), one package per domain, and `registry.py`. The Shed API serves one domain itself, Sentinel's SRE (`domains/sre/`): `domain.py` (`SreDomain` and its events), `incidents.py` (`IncidentWorkflow`, run by the SRE agent), and `reviews.py` (`ReviewWorkflow`, run by the PR Review agent), each with its statuses, graph, tones, titles, actions decided by the pure rules, and links. Every external trigger enters through a domain's events (`/api/sre/events/alertmanager`, open even while SRE is disabled, and `/api/sre/events/check`). `shed/stonks/api/src/stonks/api/` is the Stonks backend (`datasets.py`, `store.py`, `server.py`): the universe snapshots and reference documents as JSON, and `prices`, read with `pyarrow` from `curated/prices/trade_date=<trade_date>/`. `shed/shed/ui/` is a static React app the API serves from the same `shed` image: `src/api/` loads `/domains.json` and each domain's manifest, `src/components/` holds the shared shell (`DomainTiles`, `WorkflowDomainView` with the state machine and records, `DataDomainView` with `DataGrid`, generic record actions and a generic record view), `src/tones.tsx` takes state tones from the backend, `src/components/DomainWorkflows.tsx` shows a domain's workflows as tabs, and `src/domains/<domain>/<workflow>/` holds a workflow's own record view (`sre/incidents/`, `sre/reviews/`), loaded lazily through `src/domains/registry.ts`; a workflow without one gets the generic view. The URL hash is `#/<domain>/<workflow or dataset>/<record>`. The shed chart's HTTPRoute is the only public route: each `domains` entry with a `backend` (`service`, `port`) sends its `api` path to that Service (`/api/stonks` to `stonks-api`), and the rest of the hostname goes to `shed`, whose API serves `/api` and whose bundled UI serves the rest; domain charts expose only a Service. `shed/sentinel/workflow/src/sentinel/workflow/sre/incidents/` and `shed/sentinel/workflow/src/sentinel/workflow/sre/reviews/` own workflow execution, write repositories, and state machines. `shed/sentinel/sre/src/sentinel/sre/incidents/` and `shed/sentinel/sre/src/sentinel/sre/reviews/` contain isolated Kafka consumers that run agents from `shed/sentinel/agents/`; Workflow decides external side effects; `shed/sentinel/executor/src/sentinel/executor/` alone performs them.
- Keep packages flat and dependencies direct: workflow → repository → pure state machine. Put status transitions in each domain's `machine.py`, not in repository code. Do not nest calls in logic: assign each call's result to a named variable before passing it to another call, returning it, or testing it (write `queued = with_event(...)` then `return Accepted(queued)`, not `return Accepted(with_event(...))`). Declarative constructs are exempt: SQLAlchemy column types and query builders (`mapped_column(DateTime(...))`, `select(func.count())`) and `SettingsConfigDict(yaml_file=config_files(...))`. Apply them through `postgres.apply_event`. The workflow graphs in `sentinel.core.state.workflows` are the enforced contract: each machine's `transition` rejects a status change the graph does not list, so a new status change needs its edge there. Use the pure rules in `sentinel.core.state` (`incident_rules.py`, `review_rules.py`) and policy functions for decisions, with I/O at the edges. Keep LangChain imports inside the agents: `shed/agents/`, `shed/sentinel/agents/`, and `stonks.dividends.agent`.
- Use `sentinel.core.errors.NotFound` and `Conflict` for expected API errors. The API maps `SentinelError` to 404/409; unexpected built-in exceptions remain 500s.
- Kafka requests, agent and executor commands, and results use Pydantic contracts in `shed/sentinel/core/src/sentinel/core/kafka/contracts.py`; executor payloads live in `shed/sentinel/core/src/sentinel/core/contracts/executor.py`. Credentials use `SecretStr` and are unwrapped only at client boundaries.
- `shed/knowledge/` is the knowledge service. It owns one ClickHouse database, `knowledge`, and its user (`infra/knowledge/sql/`); the tables in it belong to the domains that use them: each domain's module creates its own pair (Sentinel's `knowledge.sentinel_documents` and `knowledge.sentinel_chunks` in `infra/sentinel/sql/<version>/clickhouse/30-knowledge/`), and the knowledge chart's `config/knowledge.yaml` names, per domain, those `tables`, its `bucket`, and its `collections` (each indexed from `context/<collection>/knowledge/` with the `tags` a search may filter on). The API is versioned and its contracts live in `knowledge.client.contracts`: `GET /v1/domains` (every domain, its collections and tags, and whether it is indexed) and `POST /v1/domains/{domain}/search` (`KnowledgeSearchRequest`: `query`, `collection`, `tag`; `KnowledgeSearchResponse`: `results`, each `RetrievedContext` with `content`, `source`, `score`), answering 404 for an unknown domain or collection and 503 until that domain's first indexing pass succeeded; `/healthz` and `/readyz` (ready once every domain had a first pass and ClickHouse answers). Callers use `KnowledgeClient(endpoint, domain)`; Sentinel's endpoint and domain are its chart's `knowledge.url` and `knowledge.domain`. One process indexes every domain from its own bucket, with that domain's credentials (`KNOWLEDGE_<DOMAIN>_S3_ACCESS_KEY_ID` and `..._SECRET_ACCESS_KEY`, from the chart's own `secret`, keys `<DOMAIN>_S3_ACCESS_KEY_ID` and `<DOMAIN>_S3_SECRET_ACCESS_KEY`), on startup and every `rag.index_interval_seconds`; one domain's failure never stops another. Embeddings are always local: `shed/knowledge/Dockerfile` pins the model with `ARG EMBEDDING_REVISION` and fetches each file with `ADD --checksum`, exporting the revision as `KNOWLEDGE_RAG__EMBEDDING_REVISION`; `knowledge.yaml` names only the fastembed model and its local path. A new domain adds its two tables to its own SQL folder, an entry in `config/knowledge.yaml`, and its two `<DOMAIN>_S3_*` keys in `knowledge-secrets`.
- `shed/sentinel/workflow/src/sentinel/workflow/runner.py` runs both enabled state machines in one Workflow process; the workflow reads what it decides on directly (GitHub pull requests with read-only installation tokens of the GitHub App, Alertmanager's alerts, knowledge search) and posts Discord notifications, but changes nothing else: every change to GitHub or the cluster is an `ExecutorCommand` that sentinel-executor alone performs, and the API holds no GitHub credentials; `shed/shed/ui/` is React. `infra/sentinel/chart/` is the chart; its `config/` holds the Homelab site configuration that Sentinel runs with.
- Workstation CLI tools are managed by dotfiles. CI installs pinned Helm with `azure/setup-helm`; component images install only their own runtime dependencies and required tools.

## Data and deployment conventions

- PostgreSQL stores current incident and review fields in columns and structured histories in JSONB. Delete removes the row. Apply `infra/sentinel/sql/` to fresh databases with `task sql MODULE=sentinel`, which runs the highest version folder from scratch; there are no application migrations or upgrade scripts. While a release is in development, change its folder (currently `1.0.0`) in place.
- `task sql` and `task s3` deploy one module's fresh-install SQL or S3 content: `MODULE=<module>` selects it, or `gum` asks among the modules with hosts of that kind (`sql`: `knowledge`, `sentinel`; `s3`: `sentinel`, `stonks`), and anything after `--` goes to `ansible-playbook` (`task sql MODULE=sentinel -- --limit sentinel-clickhouse`). They run `infra/ansible/sql.yaml` or `s3.yaml` with `-e module=<module>` on the hosts in both the kind group (`sql`, with the engine groups `postgresql` and `clickhouse`, or `s3`) and the module group (`knowledge`, `sentinel`, `stonks`); a module without such hosts fails before anything runs. The workstation reaches every service directly (no port forwards). Inventory hosts are `<module>-<target>` (`knowledge-clickhouse`, `sentinel-clickhouse`, `sentinel-postgresql`, `sentinel-s3`, `stonks-s3`, `stonks-logs`, which only creates the `logs` bucket); an engine's or the S3 endpoint's shared settings live in `group_vars/<group>/main.yaml`, a host's own in `host_vars/<host>/main.yaml`, and 1Password lookups only in `secrets.yaml`; there are no role defaults. `roles/sql` deploys `infra/<module>/sql/<highest version>/<engine>/` with `roles/sql/tasks/<engine>.yaml`, the host's `sql_engine`, one task per datastore running its native client (`psql`, `clickhouse client`) in one session, and fails when an engine folder has no host of the module; a new datastore is a new engine group with its task files, and a module's new SQL target is one `<module>-<engine>` host. ClickHouse authenticates the client as `admin` and renders `*.sql.j2` files; the `knowledge` user's password is rendered only into the SQL sent to the client and never committed. Apply `task sql MODULE=knowledge` before a domain's ClickHouse SQL, which creates that domain's tables in the `knowledge` database. The playbooks must pass `ansible-lint --profile production`.
- The chart owns Sentinel resources in its release namespace and Sentinel's Strimzi `KafkaTopic`s in the Kafka namespace (`kafka.topicNamespace`), rendered from the same `kafka.topics` map the processes read and kept on uninstall. Homelab owns database roles, Kafka users and their ACLs, secrets, and site values. One-time initialization (the PostgreSQL schema, Sentinel's knowledge tables, prompts and knowledge) runs by hand through `task sql MODULE=sentinel` and `task s3 MODULE=sentinel`, after `task sql MODULE=knowledge` (`infra/ansible/`); add new initialization targets as inventory hosts of their module, not as scripts or Jobs. Do not embed credentials here.
- Reconcile GitHub side effects on replay. Preserve manual-action claims; submissions, merges, and fix pushes hold no claim, and the executor's GitHub reconciliation keeps a replay from repeating a PR, merge, or fix commit. Agents self-manage: the hard boundary is that agents never read secrets (no Secrets RBAC, blocked credential paths and program execution in agent commands, redacted output, credential-free fixes); do not add other approval gates. PR auto-merge requires passing checks and the configured risk and confidence levels; there are no path, kind, author, or deletion gates, so PR Review merges SRE fix PRs like any other. Incident fixes may change any repository-relative path and kind and must contain no credential material. Nothing retries automatically: a failed incident or review stays failed until an operator replays it from the UI (replay and retry are one operation, called Replay). A blocked review is fixed only when an operator chooses Fix it; the fix is pushed to the PR only if the fixed revision passes the checks and contains no credential material. Manual actions are operations the agents cannot perform (for example job cleanup) and are the one step that waits for operator approval in the UI; sentinel-executor runs approved single commands without a shell, under its narrow `sentinel-executor` ClusterRole.
- The API has no authentication; it is reachable only through the internal gateway. Kafka consumers do not retry: a message whose handling fails marks the incident or review its `record_id` names as failed when the message's workflow owns it (`DomainWorkflow`), then is logged and skipped. Operators replay only from the UI; nothing re-runs work on its own. Entering a terminal status (incidents: `awaiting`, `blocked`, `failed`, `resolved`; reviews: `blocked`, `failed`, `merged`) makes the workflow post it to Discord with `DISCORD_WEBHOOK_URL` (`shed/sentinel/workflow/src/sentinel/workflow/discord.py`, which redacts the webhook URL from `httpx` logs); a notification that cannot be sent never changes the record.
